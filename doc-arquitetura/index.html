1. Visão Geral e Caso de Uso

O demo-customer-service é um microsserviço que centraliza o ciclo de vida de cadastro de clientes de um ecossistema maior (por exemplo, uma plataforma financeira de crédito). Ele permite criar, editar, consultar, filtrar e remover clientes, além de integrar uma consulta de score de crédito externo e trocar informações com outros sistemas de forma assíncrona via RabbitMQ.

Caso de uso (cenário típico): um usuário ADMIN cadastra um cliente novo (nome, CPF e e-mail). Na sequência, o sistema:
  1. valida os dados e impede CPF duplicado;
  2. persiste o cliente com status ACTIVE;
  3. publica o evento CUSTOMER_CREATED no RabbitMQ para que outros serviços reajam (CRM, BI, antifraude, e-mail de boas-vindas etc.);
  4. disponibiliza a consulta GET /customers/{id}/score, que busca o score de crédito em um serviço externo usando o CPF do cliente;
  5. consome eventos CUSTOMER_STATUS_CHANGE (ex.: bloquear ou reativar um cliente) de forma idempotente.
Toda a API é protegida por OAuth 2.0 / JWT com perfis de acesso USER (somente leitura) e ADMIN (acesso total).

O foco do projeto é demonstrar, em código, boas práticas de engenharia de software para um contexto de microservices: arquitetura hexagonal, resiliência em integrações externas, mensageria idempotente com dead-letter queue, segurança por tokens e execução da solução inteira com um único comando Docker Compose.

3. Arquitetura Funcional (Hexagonal — Ports and Adapters)

O microsserviço foi construído seguindo a Arquitetura Hexagonal (Ports and Adapters), separando o núcleo de negócio (domínio + casos de uso) das tecnologias externas (Spring, JPA/Hibernate, RabbitMQ, HTTP).

Por que Hexagonal?

  • Isolamento das regras de negócio: a entidade Customer e os casos de uso não conhecem Spring, banco ou mensageria.
  • Facilidade de teste: casos de uso e lógica de domínio são testados unitariamente sem subir o contexto do Spring (JUnit 5 + Mockito).
  • Resiliência e troca de adaptadores: a integração externa de Score pode ser simulada/substituída apenas trocando o adaptador de saída.
REST Controller
(adaptador de entrada) → Use Cases
(Create / ChangeStatus / GetScore) → Domain
(Customer, ScoreInfo, Ports) ← Adapters de saída
(JPA, RabbitMQ, HTTP)
Regra: dependências sempre apontam para dentro (o domínio não depende de ninguém).

Estrutura de pacotes

com.ramoscodev.customer
├── domain/                      # Core da aplicação (sem dependência de framework)
│   ├── model/                   # Customer, CustomerStatus, ScoreInfo
│   ├── exception/               # CustomerNotFoundException, DuplicateCpfException
│   └── port/out/                # CustomerRepositoryPort, ScoreClientPort, EventPublisherPort
├── application/
│   └── usecase/                 # CreateCustomerUseCase, ChangeCustomerStatusUseCase, GetCustomerScoreUseCase
└── infrastructure/              # Adaptadores de entrada e saída + config
    ├── adapters/
    │   ├── in/web/              # CustomerController + DTOs (CustomerRequestDTO, CustomerResponseDTO)
    │   ├── in/messaging/        # CustomerStatusListener + CustomerStatusChangeEvent (idempotente)
    │   ├── out/persistence/     # CustomerEntity, CustomerRepositoryAdapter, ProcessedMessageEntity
    │   ├── out/http/            # ScoreClientAdapter + ScoreHttpClient (Resilience4j)
    │   └── out/messaging/       # RabbitMQEventPublisherAdapter
    └── config/                  # SecurityConfig, RabbitMQConfig, RestTemplateConfig, GlobalExceptionHandler

Componentes-chave

  • Ports de saída (interfaces no domínio): CustomerRepositoryPort, ScoreClientPort, EventPublisherPort — definem o que o domínio precisa, sem dizer como.
  • Adaptadores de saída (implementações na infraestrutura): CustomerRepositoryAdapter (JPA), ScoreClientAdapter/ScoreHttpClient (RestTemplate + Resilience4j), RabbitMQEventPublisherAdapter (RabbitTemplate).
  • Adaptadores de entrada: CustomerController (REST) e CustomerStatusListener (RabbitMQ listener).
  • Configuração: SecurityConfig (JWT Resource Server + regras por perfil), RabbitMQConfig (filas, exchanges, DLX), GlobalExceptionHandler (@ControllerAdvice).

4. Fluxos Principais

4.1 Cadastro de cliente + evento (RF01/RF04)

  1. O CustomerController recebe o POST /customers com nome/CPF/e-mail.
  2. O CreateCustomerUseCase verifica CPF duplicado (DuplicateCpfException), define status ACTIVE e persiste via CustomerRepositoryPort.
  3. O RabbitMQEventPublisherAdapter publica o evento CUSTOMER_CREATED na exchange customer.exchange, routing key customer.created, que fica na fila customer.created.queue.

4.2 Consulta de score com resiliência (RF03/RNF04)

  1. GET /customers/{id}/score → GetCustomerScoreUseCase busca o cliente e obtém o CPF.
  2. ScoreHttpClient chama o serviço externo GET /scores/{cpf} protegido por Retry (2 tentativas), TimeLimiter (2s) e Circuit Breaker (janela 5, 50% de falhas, open 10s).
  3. Se falhar/estourar o tempo, o fallback retorna score=0, classification=UNAVAILABLE (resposta degradada graciosa).

4.3 Consumo de mudança de status com idempotência (RF05/RNF03)

  1. CustomerStatusListener consome customer.status.change.queue.
  2. Verifica se o eventId já existe em tb_processed_messages; se sim, descarta (ACK) sem reprocessar.
  3. Executa ChangeCustomerStatusUseCase e registra o eventId na tabela de mensagens processadas — tudo na mesma transação.
  4. Em caso de falha irreversível, a mensagem vai para a DLQ customer.status.change.dlq via Dead Letter Exchange.

4.4 Autenticação e autorização (RF06/RNF02)

  1. O cliente solicita um token no Keycloak (client customer-service, direct access grants).
  2. O SecurityConfig atua como Resource Server: valida o JWT pelo issuer e converte o claim realm_access.roles em autoridades ROLE_USER/ROLE_ADMIN.
  3. Regras: GET /customers/** exige USER ou ADMIN; demais operações (POST/PUT/DELETE) exige ADMIN.

5. Requisitos Funcionais (RF)

RF04 Publicação de Evento de Criação — ao criar cliente com sucesso, publica CUSTOMER_CREATED no RabbitMQ. RabbitMQEventPublisherAdapter → exchange customer.exchange → fila customer.created.queue.
RF05 Processamento Assíncrono de Status — consome CUSTOMER_STATUS_CHANGE e atualiza o status do cliente. CustomerStatusListener (idempotente por eventId) → ChangeCustomerStatusUseCase.
RF06 Autorização Baseada em Perfil — USER apenas consulta (GET); ADMIN acesso total. SecurityConfig: GET /customers/** → hasAnyRole(USER, ADMIN); demais → hasRole(ADMIN).

Configuração de resiliência (application.yml)

resilience4j:
  circuitbreaker:
    instances:
      scoreService:
        slidingWindowSize: 5          # janela de avaliação
        failureRateThreshold: 50       # abre com ≥ 50% de falhas
        waitDurationInOpenState: 10s   # tempo em estado OPEN
        permittedNumberOfCallsInHalfOpenState: 3
  timelimiter:
    instances:
      scoreService:
        timeoutDuration: 2s           # estoura chamadas acima de 2s
  retry:
    instances:
      scoreService:
        maxAttempts: 2                 # 1 chamada + 1 nova tentativa
        waitDuration: 500ms

Base URL: http://localhost:8082. Todos os endpoints exigem o header Authorization: Bearer <token>.

MétodoEndpointPerfisDescrição

PUT/customers/{id}ADMINAtualiza nome/CPF/e-mail (retorna 200).
DELETE/customers/{id}ADMINRemove um cliente (retorna 204).
GET/customers/{id}USER, ADMINBusca cliente por ID.
GET/customersUSER, ADMINLista todos.
GET/customers?status=INACTIVEUSER, ADMINFiltra por status.
GET/customers/search?name=...USER, ADMINBusca por nome (case-insensitive).
GET/customers/{id}/scoreUSER, ADMINScore de crédito do cliente.

Corpos de exemplo

Requisição de criação:

{
  "name": "João da Silva",
  "cpf": "12345678901",
  "email": "joao@email.com"
}

Resposta de criação (201):

{
  "id": 1,
  "name": "João da Silva",
  "cpf": "12345678901",
  "email": "joao@email.com",
  "status": "ACTIVE"
}

Resposta do score (200) e resposta degradada (200):

{ "cpf": "12345678901", "score": 750, "classification": "LOW_RISK" }
{ "cpf": "12345678901", "score": 0, "classification": "UNAVAILABLE" }

Erros possíveis

  • 400 — validação de campos (nome, CPF com 11 dígitos, e-mail) ou parâmetro inválido.
  • 401 — token ausente/ inválido/expirado.
  • 403 — perfil sem permissão (ex.: USER tentando criar).
  • 404 — cliente não encontrado.
  • 409 — CPF já cadastrado.

8. Sugestões e Melhorias

S1 Transactional Outbox — hoje o evento CUSTOMER_CREATED é publicado dentro da mesma transação do cadastro; se o RabbitMQ estiver indisponível nesse instante, a publicação pode falhar. A melhor prática é persistir o evento em uma tabela outbox na mesma transação e publicar com um relé (outbox pattern) para garantir entrega.
S2 Observabilidade — adicionar Micrometer com métricas do Resilience4j (as do scoreService já estão habilitadas via registerHealthIndicator), Prometheus + Grafana, e distribui tracing com Micrometer Tracing.
S3 Documentação de API — integrar OpenAPI/Springdoc com Swagger UI (springdoc-openapi-starter-webmvc-ui) para descoberta e testes interativos dos endpoints.
S4 Migrações de schema — trocar ddl-auto: update por Flyway ou Liquibase para versionar o banco e permitir evolução segura em produção.
S5 Segredos e configuração — mover credenciais (usuário/senha do banco, credenciais do RabbitMQ, client secret) para variáveis de ambiente gerenciadas (Secret Manager / Kubernetes Secrets / Vault), evitando valores fixos em configuração.
S6 Validação de CPF — além dos 11 dígitos, validar os dígitos verificadores do CPF (algoritmo oficial) para impedir CPFs inválidos.
S7 Paginação — em listagens de grande volume, adicionar paginação (Pageable) em GET /customers e /search.
S8 CI/CD — pipeline de CI/CD (ex.: GitHub Actions): mvn clean test, análise estática (SonarQube), build e publicação da imagem no registry, deploy (Helm/Kubernetes ou ECS).
S9 Cache do score — o score varia pouco; um cache (Redis/Caffeine) por CPF reduz a carga sobre o serviço externo e a latência.
S10 Testes de contrato — usar testes de contrato (Pact) entre consumidores e provedores, e manter os mocks do WireMock alinhados ao contrato real.
S11 Segurança adicional — explorar client credentials para comunicação serviço-a-serviço, escopos por operação e revogação de tokens; hoje apenas realm_access é mapeado.

9. Onde Esta Aplicação e Arquitetura Podem Ser Utilizadas

Domínios / cenários de negócio

  • Fintechs e bancos digitais: onboarding de clientes, cadastro para pré-análise de crédito e consulta de score — exatamente o fluxo simulado aqui.
  • Plataformas de CRM e cobrança: centralização do ciclo de vida do cliente e integração com outras áreas por eventos.
  • E-commerce e marketplaces: cadastro de contas/lojas com notificação assíncrona de criação e atualização de status (ativo/inativo).
  • Saúde / educação / governo: qualquer sistema que precisa manter cadastros regulamentados com trilha de eventos e atualização assíncrona de status.

Padrões e situações técnicas

  • Arquitetura baseada em eventos (event-driven): quando outros serviços precisam reagir à criação/alteração de clientes sem acoplamento síncrono.
  • Integrações com sistemas externos instáveis ou lentos: o padrão de Circuit Breaker + Retry + Timeout + Fallback é ideal quando uma dependência (como bureaus de crédito) pode falhar ou demorar.
  • Mensageria com entrega garantida e idempotência: quando a entrega "pelo menos uma vez" do broker pode gerar duplicatas e o consumidor precisa ser idempotente.
  • Migração de monólitos: a arquitetura hexagonal facilita extrair o domínio de cliente de um sistema legado sem acoplar tecnologia.
  • Provas de conceito e avaliações técnicas: serve como template reutilizável de microsserviço "sênior" com boas práticas completas e demo Docker Compose.

Quando não é a melhor escolha

  • CRUD simples com um único time e baixa escala — um monólito Spring Boot único reduz a complexidade operacional.
  • Quando não há demanda por consumo assíncrono — a mensageria adiciona complexidade sem retorno.
  • Equipes pequenas sem maturidade em observabilidade/operacional de infraestrutura distribuída.

Passo 3 — Obter um token JWT no Keycloak

Usuário admin-user (perfil ADMIN — pode escrever):

curl -X POST http://localhost:8080/realms/customer-realm/protocol/openid-connect/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "client_id=customer-service" \
  -d "username=admin-user" \
  -d "password=admin123" \
  -d "grant_type=password"

Guardar apenas o token em uma variável:

TOKEN=$(curl -s -X POST http://localhost:8080/realms/customer-realm/protocol/openid-connect/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "client_id=customer-service" -d "username=admin-user" \
  -d "password=admin123" -d "grant_type=password" \
  | python3 -c "import sys,json;print(json.load(sys.stdin)['access_token'])")

Usuário de perfil somente-leitura: regular-user / user123.

Passo 5 — Testar a resiliência (tempo de resposta)

O WireMock carrega dois stubs em score-mock/mappings/:

  • score_success.json — prioridade 1, responde 750 imediatamente;
  • score_timeout.json — atrasa a resposta em 5 segundos (acima do timeout de 2s).

Para simular lentidão, remova o stub de sucesso e deixe apenas o de timeout:

# Remove o stub de sucesso (o WireMock recarrega a pasta automaticamente)
rm score-mock/mappings/score_success.json

# A consulta ao score deve demorar ~2s e retornar o fallback:
curl http://localhost:8082/customers/1/score -H "Authorization: Bearer $TOKEN"
# → {"cpf":"12345678901","score":0,"classification":"UNAVAILABLE"}

# Restaura o stub de sucesso (e o container para recarregar, se preciso)
git checkout -- score-mock/mappings/score_success.json
docker compose restart wiremock

Passo 6 — Testar o processamento assíncrono e a idempotência

Simule o envio de dois eventos CUSTOMER_STATUS_CHANGE idênticos (mesmo eventId) diretamente no RabbitMQ: 

# 1ª mensagem: altera o status do cliente 1 para INACTIVE
curl -X POST http://localhost:15672/api/exchanges/%2f/amq.default/publish \
  -u guest:guest -H "Content-Type: application/json" \
  -d '{"properties": {},
       "routing_key": "customer.status.change.queue",
       "payload": "{\"eventId\": \"uuid-1234-5678\", \"eventType\": \"CUSTOMER_STATUS_CHANGE\", \"customerId\": 1, \"status\": \"INACTIVE\"}",
       "payload_encoding": "string"}'

# 2ª mensagem: duplicada (mesmo eventId) → deve ser ignorada
curl -X POST http://localhost:15672/api/exchanges/%2f/amq.default/publish \
  -u guest:guest -H "Content-Type: application/json" \
  -d '{"properties": {},
       "routing_key": "customer.status.change.queue",
       "payload": "{\"eventId\": \"uuid-1234-5678\", \"eventType\": \"CUSTOMER_STATUS_CHANGE\", \"customerId\": 1, \"status\": \"INACTIVE\"}",
       "payload_encoding": "string"}'

Resultado esperado:

  • O status do cliente 1 muda para INACTIVE;
  • a tabela tb_processed_messages tem exatamente 1 registro (o eventId);
  • o log da aplicação exibe "Evento com ID uuid-1234-5678 já foi processado. Ignorando.";
  • as filas customer.status.change.dlq e customer.status.change.queue ficam vazias.

Confira as filas e a mensagem CUSTOMER_CREATED pendente em customer.created.queue pelo console do RabbitMQ (http://localhost:15672).
